# Правила агентной разработки HandOff

## Обязательное чтение

- Прочитай этот файл в начале каждой сессии и перед первым изменением кода. После потери или сокращения контекста перечитай его. Соблюдай правила при реализации, ревью и рефакторинге.
- Перед изменением конкретной папки проверь вложенные `AGENTS.md`: они уточняют правила своей области.
- `README.md` и `docs/PRODUCT.md` читай по необходимости или по просьбе пользователя. При изменении продуктового поведения сверяйся с `docs/PRODUCT.md`, если задача не содержит достаточных требований.
- Прямые указания пользователя имеют приоритет над этими правилами в пределах системных ограничений. Не выдавай предпочтение навыка за требование пользователя.

## Архитектура

- Стек проекта: React, TypeScript, Tailwind CSS. Используй существующую структуру, инструменты и зависимости.
- Применяй инкапсуляцию, разделение ответственности и композицию. ООП используй там, где оно упрощает предметную логику; классы и наследование не обязательны для каждого модуля.
- Пиши React-компоненты функциями. Связанную с React логику выноси в кастомные хуки, чистые вычисления в функции, доступ к данным и внешним системам в сервисы. Классы вводи при реальной необходимости состояния и жизненного цикла объекта.
- Собирай интерфейс из UI-примитивов, переиспользуемых компонентов и самостоятельных функциональных блоков. Перед созданием нового элемента ищи существующий аналог.
- Соблюдай назначение слоев: `app` связывает приложение, `pages` собирает страницы, `features` содержит пользовательские сценарии, `shared` содержит общие примитивы и инфраструктуру. Общий код не должен зависеть от страниц и конкретных сценариев.
- Держи код рядом с местом использования. Переноси его в общий слой при фактическом повторном использовании или явно общей ответственности.
- Выбирай минимальное решение, закрывающее задачу. Не добавляй абстракции, фабрики, универсальные конфиги, зависимости или архитектурные слои на будущее.

## Компоненты и TypeScript

- Один компонент или модуль отвечает за одну понятную задачу. Выделяй части по самостоятельной ответственности, повторному использованию или сложности, без произвольных лимитов строк.
- Описывай явный контракт props. Используй композицию через `children` и небольшие предметные props; избегай множества флагов, меняющих назначение компонента.
- Не смешивай UI-примитивы с бизнес-логикой и сетевыми запросами. Побочные эффекты выполняй в подходящих обработчиках, хуках или сервисах, никогда во время рендера.
- Состояние размещай как можно ближе к потребителю. Не храни в состоянии значения, которые можно вычислить из props или текущих данных. Эффекты используй для синхронизации с внешними системами.
- Используй строгую типизацию, `unknown` и сужение типов на внешних границах. Не обходи ошибки через необоснованные `any`, приведения, `!`, `@ts-ignore` или отключение линтера. Узкие обходы несовпадения типов с поддерживаемыми веб-API допускаются по руководству с пояснением причины.
- Компоненты и типы именуй в `PascalCase`, функции и переменные в `camelCase`, хуки с префиксом `use`. Имена должны объяснять назначение; сохраняй принятые в проекте соглашения для файлов и экспортов.
- Комментарии объясняют причину решения или ограничение. Не пересказывай ими очевидный код.
- Не добавляй мемоизацию, глобальное состояние и другие оптимизации без конкретной необходимости.

## Интерфейс, верстка и текст

- Используй семантический HTML и нативные возможности платформы. Действия оформляй кнопками, переходы ссылками, поля связывай с видимыми подписями.
- Обеспечивай клавиатурную навигацию, видимый фокус, читаемый контраст и доступные имена элементов. Учитывай `prefers-reduced-motion`.
- Верстка должна работать на узких и широких экранах, с длинным текстом и увеличенным масштабом. Не маскируй ошибки расположения глобальным скрытием переполнения.
- Используй Tailwind и общие токены проекта для согласованных отступов, размеров, цветов и типографики. Собственный CSS добавляй, когда он делает решение понятнее.
- Для асинхронных сценариев предусматривай загрузку, пустой результат, ошибку и успешное состояние. Показывай подтверждение только после фактического успеха операции.
- Пропускай названия, кнопки, подсказки, ошибки и другие тексты сервиса через `humanizer`. Сохраняй смысл макета, исправляй сухие и неестественные формулировки. Не выдумывай факты и возможности.
- Не используй декоративные точки между словами, длинные тире, шаблонные градиенты и свечения. Не переноси нейрослоп из макета в реализацию. Сохраняй обычную пунктуацию и технические обозначения там, где они нужны по смыслу.

## Порядок работы и проверки

- Сначала прочитай затрагиваемый код, найди аналоги и проследи поток данных. При исправлении ошибки проверь места вызова и устрани причину на общем подходящем уровне.
- Меняй только относящееся к задаче. Сохраняй чужие незакоммиченные изменения, не откатывай их и не включай в собственные коммиты.
- Проверяй внешние данные на границах, обрабатывай ошибки, не добавляй секреты в код, логи и Git.
- После изменения кода запускай доступные `npm run lint` и `npm run build`. Для нетривиальной логики добавляй минимальную воспроизводимую проверку поведения. Для правки только документации сборка не требуется.
- Интерфейс проверяй в браузере на узком и широком экране, включая взаимодействия, клавиатуру и состояния. Если проверка недоступна, прямо укажи это.
- Не утверждай, что проверка пройдена, если она не запускалась или завершилась ошибкой. В ответе укажи результат, выполненные проверки и оставшиеся ограничения.

## Git и коммиты

- Перед подготовкой коммита проверь `git status` и diff. Включай только файлы и изменения текущей задачи; один коммит должен иметь одну понятную цель.
- Создавай коммиты, отправляй изменения и переписывай историю только в рамках поручения пользователя. Само наличие правил коммитов не является поручением сделать коммит.
- Строго используй Conventional Commits: `<type>(<scope>): <описание>`. Для общей задачи без отдельной области допустимо `<type>: <описание>`.
- Типы: `feat`, `fix`, `refactor`, `docs`, `style`, `test`, `build`, `ci`, `chore`, `perf`, `revert`. `style` относится к форматированию кода без изменения поведения; изменение внешнего вида классифицируй по сути задачи.
- Scope обозначает затронутый компонент или область проекта. Описание пиши по-русски, кратко, без точки в конце, в безличной форме прошедшего времени со страдательным значением: «добавлено», «реализовано», «исправлено», «удалено».
- Не используй «я», «мы», повелительное наклонение, расплывчатые сообщения вроде «правки» или «обновления». Для несовместимого изменения ставь `!` после типа или scope и поясняй его в `BREAKING CHANGE:`.

Примеры:

```text
feat(AdminPanel): реализовано добавление нового пользователя в таблице
fix(LoginForm): исправлено отображение ошибки авторизации
refactor(UserCard): вынесено форматирование данных в хук
docs: добавлены правила агентной разработки
```
